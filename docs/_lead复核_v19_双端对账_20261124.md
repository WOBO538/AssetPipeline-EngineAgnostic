## 3. 索引对齐（本单命门）——lead 单独查过

Unity 读回 `instancesDetail`：**1,892 条，`matched=true` 1,892/1,892**，分项 conifer 1324 / broadleaf 568。

- `index` 是**每个 asset 内部的下标**（conifer 0–1323、broadleaf 0–567），所以全局看会有重复数字——这是设计如此；重复检测用的键是 **`(assetId, index)`**（代码 L1023），`dup=0` 说明没有两 asset 撞键，也没有同 asset 内重复下标；
- Unity 侧每条明细都拿 manifest 期望 transform 逐项比对后写 `matched`（L628 比较 x/y/z 与 yaw），**不是用场景遍历顺序冒充 manifest 顺序**；顺序错位会以 `matched=false` 暴露——这点与 TRAE 的说法一致，我独立确认了 1,892/1,892。

坐标换算也逐位核对过：manifest `t=[0.8713, 96.4027, -0.2142]`（UE x,y,z）→ Unity `t=[0.8713, -0.2142, 96.4027]`（x,z,y），`yaw=-152.816`（UE 152.816 取反），与 v1.8 的权威换算一致。

## 5. 碰撞证据（不是 setter 返回值）

`collision{enabled=True, profile='BlockAll', instanceCount=1892, meshHasCollision=True}`：
- `instanceCount` 是 **ISM 实例数求和**（1892），不是组件数 1；
- `meshHasCollision` 读的是网格 `body_setup` 里**实际烘出的碰撞元素数**（凸包元素计数），不是 `set_collision_enabled` 的返回；
- 关碰撞后 profile 变 `Custom`、`enabled=False` —— 反向验证能如实反映状态。

## 6. 新鲜度门禁（以后会踩的约束）

`--parity-check` 要求两份证据文件的 mtime **晚于 manifest**，所以顺序固定：

```
--real-multi  →  --unity-placements-check  →  --parity-check
```

跳步会被拦（`stale` 分支直接 FAIL）。这条已写进 README，我复验时也按这个顺序跑。
